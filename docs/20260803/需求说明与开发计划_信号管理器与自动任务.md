## 一、需求说明

### 1.1 模块定位

本需求包含两个核心模块：**信号管理器 (Signal Manager)** 和 **自动任务 (Auto Task)**。

- **信号管理器**：统一管理来自不同来源的交易信号（随机信号、外部信号、策略信号等），提供标准的信号格式与信号获取接口。
- **自动任务**：可配置的自动化下单引擎，根据预设的信号来源和调度规则，自动执行交易下单，并记录完整的执行日志。

### 1.2 功能需求详述

#### 功能一：信号管理器 (Signal Manager)

**目标**：支持通用外部信号的传入与适配，统一信号格式。

- **默认信号：随机信号**
  - **信号类型**：随机方向信号
  - **标的代码生成规则**：`btc-updown-4h-[当前时间戳(秒)]`，例如 `btc-updown-4h-1785744000`
  - **下单金额**：固定为 1 USDC (1U)
  - **下单方向**：随机生成 `UP` 或 `DOWN`

- **统一信号格式规范**

  | 字段 | 类型 | 必填 | 说明 | 示例 |
  |------|------|------|------|------|
  | `symbol` | string | 是 | 标的代码 | `btc-updown-4h-1785744000` |
  | `amount` | float | 是 | 下单金额（USDC） | `1` |
  | `direction` | enum | 是 | 下单方向：`UP` 或 `DOWN` | `UP` |
  | `source` | string | 否 | 信号来源标识 | `random` |
  | `timestamp` | int | 否 | 信号时间戳 | `1785744000` |

- **可扩展的信号源架构**：预留外部信号接入点（如通过 HTTP API 推送、Redis 订阅等），当前先实现随机信号源。

#### 功能二：自动任务 (Auto Task)

**目标**：提供任务的创建、配置、启停、监控全生命周期管理。

- **默认任务：随机自动下单任务**
  - **任务名称**：`随机任务每5分钟下一单`
  - **调度周期**：每 5 分钟执行一次
  - **信号来源**：随机信号
  - **执行逻辑**：获取信号 → 初始化网关 → 下单 → 记录日志

- **任务管理 (CRUD)**

  | 操作 | 说明 |
  |------|------|
  | **新增任务** | 配置任务名称、信号来源、调度周期、交易网关等参数 |
  | **启用任务** | 触发网关初始化（如 F3 RELAYER 初始化），加入调度队列 |
  | **停止任务** | 从调度队列移除，释放网关资源 |
  | **编辑任务** | 修改任务参数（需先停止再编辑，或允许热更新参数） |
  | **删除任务** | 永久删除任务（软删除） |

- **任务配置项**

  | 配置项 | 类型 | 说明 | 默认值 |
  |--------|------|------|--------|
  | `task_name` | string | 任务名称 | - |
  | `signal_source` | enum | 信号来源 | `random` |
  | `gateway` | enum | 交易网关 | `polymarket_f3` |
  | `interval` | int | 调度间隔（分钟） | `5` |
  | `is_active` | bool | 是否启用 | `false` |

- **任务执行日志**
  - 每次任务执行都产生一条日志记录
  - **日志字段**：任务ID、执行时间、信号内容、下单结果（成功/失败）、交易哈希/订单ID、耗时、错误信息
  - **日志查看**：前端提供任务执行日志的完整查看界面，支持按时间范围和状态筛选

### 1.3 页面入口讨论（用户提问）

用户提出两个候选位置：

- **选项 A**：`/admin#tasks`（管理后台的任务 Tab）
  - **优点**：管理后台语义清晰，任务管理属于系统级功能
  - **缺点**：交易视角较弱，用户需切换页面

- **选项 B**：`/polymarket?tab=tasks`（Polymarket 页面的任务 Tab）
  - **优点**：交易上下文内管理，更贴合用户操作习惯
  - **缺点**：功能边界模糊，polymarket 页面已有信号/执行等功能

**建议**：考虑到任务管理涉及系统级调度（Celery Beat）和生命周期管理，且可能关联多个交易网关，**建议放在 `/admin#tasks`**。同时在 `/polymarket` 页面增加入口跳转链接，方便交易用户快速访问。

## 二、核心架构设计

### 2.1 后端模块规划

```
fwsort/
├── signals/                    # 信号模块（新建）
│   ├── __init__.py
│   ├── base.py                 # 信号基类 & 统一格式
│   ├── random_signal.py        # 随机信号实现
│   └── manager.py              # 信号管理器（工厂模式）
├── tasks/                      # 自动任务模块（新建）
│   ├── __init__.py
│   ├── models.py               # 任务 & 日志 ORM 模型
│   ├── schemas.py              # Pydantic 校验
│   ├── service.py              # 任务核心逻辑
│   ├── scheduler.py            # 任务调度引擎
│   └── executor.py             # 任务执行器
```

### 2.2 数据库模型

- **auto_tasks 表**
  - `id`, `task_name`, `signal_source`, `gateway`, `interval`, `is_active`, `config_json`, `created_at`, `updated_at`, `deleted_at`

- **auto_task_logs 表**
  - `id`, `task_id`, `executed_at`, `signal_json`, `order_result_json`, `status`(success/failed), `error_message`, `duration_ms`, `created_at`

### 2.3 API 设计

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/tasks` | 查询任务列表 |
| `POST` | `/api/tasks` | 新增任务 |
| `PUT` | `/api/tasks/{id}` | 编辑任务 |
| `DELETE` | `/api/tasks/{id}` | 删除任务 |
| `POST` | `/api/tasks/{id}/start` | 启用任务 |
| `POST` | `/api/tasks/{id}/stop` | 停止任务 |
| `GET` | `/api/tasks/{id}/logs` | 查询任务执行日志 |
| `GET` | `/api/tasks/{id}/logs/{log_id}` | 查询单条日志详情 |
| `GET` | `/api/signals/random/test` | 测试随机信号生成 |

### 2.4 Celery 调度集成

- 新增 `task_dispatcher` Celery Beat 任务，按 `interval` 分发执行任务
- 任务启用时动态注册 Beat Schedule，停止时移除
- 执行结果写入 `auto_task_logs` 表

## 三、关键设计问题（需用户确认）

### Q1：UI 入口位置
如 1.3 节讨论，建议放 `/admin#tasks`，请确认。

### Q2：网关初始化细节
用户提到启用时需完成 `F3 RELAYER 初始化`：
- **问题**：初始化是指创建新的 `PolymarketClient` 实例，还是只需验证现有实例可用性？
- **假设**：每个任务启用时独立初始化一个 F3 Relayer 实例，独立持有 API Key 和钱包地址

### Q3：信号标的代码格式
- 当前格式：`btc-updown-4h-[timestamp]`
- **问题**：时间戳是秒级还是毫秒级？是否需要添加随机后缀避免冲突？
- **建议**：秒级时间戳 + 4位随机后缀，如 `btc-updown-4h-1785744000-a1b2`

### Q4：外部信号接入扩展
- **问题**：是否需要在 V1 就预留外部信号的 HTTP/Webhook 接入接口？还是 V1 只实现随机信号？
- **建议**：V1 只实现随机信号，但架构上预留 `SignalProvider` 抽象基类

### Q5：风控与安全
- **问题**：自动下单是否需要强制风控？
  - 单日最大下单金额限制
  - 单日最大下单次数限制
  - 连续失败次数熔断机制
- **建议**：参考现有风控规则（单笔 ≤ 20% 余额、日亏 ≥ 30% 强停），自动任务默认同样适用

### Q6：任务启停状态持久化
- **问题**：服务器重启后，之前启用的任务是否自动恢复？
- **建议**：服务启动时扫描 `is_active=True` 的任务并自动恢复调度

### Q7：执行日志保留策略
- **问题**：日志保留多长时间？是否需要定期归档（热→冷存）？
- **建议**：保留 30 天热存 + 90 天冷存归档（与现有订单日志策略一致）

### Q8：多任务并发
- **问题**：多个任务同时运行时，是否支持并发执行？还是串行队列？
- **建议**：Celery 并发执行（默认 worker 数内），通过 Redis 分布式锁防止重复下单

### Q9：信号与下单的原子性
- **问题**：获取信号后，下单失败怎么办？信号是否标记为已消费？
- **建议**：下单失败时信号标记为 `failed`，支持手动重试；成功后标记为 `completed`
