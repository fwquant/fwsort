## 2. 各 WP 详细说明

### WP-06 ｜ 演示/生产数据层隔离（修复 F-1）

**目标**：`/api/*`（生产）与 `/api/demo/*`（演示）走完全不同的 SQLAlchemy Engine + Redis 实例，互不可见。

**实现要点**：
- **配置开关**：`config.py:APP_DEMO_MODE=True`（默认开启开发友好），`APP_DEMO_SQLITE_PATH="./fwsort_demo.db"`
- **双引擎**：`database.py` 同时维护 `sync_engine`（生产）+ `_demo_sync_engine`（演示），对应 `AsyncSessionLocal` / `DemoAsyncSessionLocal`、`SyncSessionLocal` / `DemoSyncSessionLocal`
- **路由镜像**：`main.py` 通过 `app.include_router(...)` 二次挂载到 `/api/demo/*` 前缀（演示版共享底层 handler），handler 内部通过 `get_async_db(request)` 解析 path 前缀动态选择引擎
- **Redis 隔离**：`redis_client.py` 同时导出 `sync_redis` + `demo_sync_redis`、`async_redis` + `demo_async_redis`；共享 Redis 时通过 `demo_redis_key()` 加 `fwsort_demo:` 前缀实现 key 命名空间隔离
- **演示模式自动 seed**：启动时若 `init_demo_db()` 检测到空库 → 自动写入 1 个 admin (demo@fwquant.com / demo123456) + 15 个演示账户

**验收**（d1_d2_smoke 步骤 3-5 + test_wp06_*）：
- 生产 admin 登录 → `/api/agent/accounts` 返回 0 条
- 演示 demo 登录 → `/api/demo/agent/accounts` 返回 15 条 ACC-DEMO1000~1014
- 两边 UID 集合交集 = ∅（隔离 OK）
- `/` 页无 `fw-demo-badge`，有 `fw-prod-footer`
- `/demo` 页有 `fw-demo-badge`，无 `fw-prod-footer`

### WP-07 ｜ 跟单自动执行任务（修复 F-3）

**目标**：订阅生效后，leader 5 分钟内的成交自动 fan-out 到所有 follower，并按 mode 计算利润分成。

**实现要点**：
- **新任务**：`fwsort.scheduler.follow_auto_copy()`（line 198），Celery beat 调度 `crontab(minute="*/5")`
- **流程**：
  1. 拉 `FollowSubscription.status=1` 的所有有效订阅
  2. 对每条订阅查 leader 账户最近 5 分钟内 `OrderExecutionLog.status=3` 的成交
  3. 检查是否已跟单（去重：`FollowOrder.leader_order_id`）
  4. 复用 `execute_follow_copy` 写 `FollowOrder` + 累加 `subscription.total_followed / total_pnl / total_share_paid`
- **同步兜底**：`admin_router.trigger_task()` 中 `follow_auto_copy` 在无 Celery broker 时走 `apply().get()` 同步执行，保证开发/演示模式可手动验证

**验收**（d1_d2_smoke 步骤 8 + test_wp07_*）：
- `POST /api/admin/trigger/follow_auto_copy` 返回 `{"result": 0, "mode": "sync-fallback"}`（无 leader 订单时返回 0 是正常的）
- `test_wp07_execute_follow_copy_creates_record`：1 USD 涨单 → follower 跟 10 USDT 赚 ≈0.01 USDT + mode=3 触发 20% 利润分成

### WP-08 ｜ 权重变更触发榜单重算（修复 F-5）

**目标**：管理员修改 `WeightConfig` 后 1 秒内 `/api/ranking/global` 反映新分数。

**实现要点**：
- **核心函数**：`fwsort.ranking_engine.refresh_redis_zset(db, rank_type=None)`（line 94）
  - 读 `WeightConfig` 中指定 rank_type（或全部）的权重
  - 对 `StrategyPerformance` 中每行调用 `composite_score(...)` 重算
  - 写回 DB + 写回 Redis ZSet
  - 返回 `{updated, rank_types}`
- **触发点**：`router/config_router.update_weights()` 写入新权重后通过 FastAPI `BackgroundTasks` 异步调用 `refresh_redis_zset`，不阻塞 HTTP 响应
- **复用**：`scheduler.refresh_realtime_rank()` 每分钟执行（也调用同一函数），全量覆盖 ZSet

**验收**（d1_d2_smoke 步骤 7 + test_wp08_*）：
- `PUT /api/ranking/config/weights?rank_type=4` → HTTP 200
- `GET /api/ranking/global` 立即按新权重排序
- `test_wp08_refresh_redis_zset_updates_scores`：3 条 perf → ZSet 写入 ≥3 条 + DB 分数更新

### WP-09 ｜ 下单事务一致性 + ES 异步化（修复 F-2 / P-9）

**目标**：`OrderExecutionLog` 入库时同时入 `outbox_event`（同事务），后台消费投 ES；ES 抖动不影响主链路 P99 < 600ms。

**实现要点**：
- **新表**：`models.OutboxEvent`（id / event_type / payload_json / status / retry_count / last_error / next_retry_at / created_at / updated_at）
- **迁移**：`migrations._NEW_TABLES_DDL` 追加 `outbox_event` DDL（SQLite/PG 双语法）
- **入队工具**：`fwsort.execution.outbox.build_order_log_event(log)` 构造 OutboxEvent；`enqueue_order_log_event(db, log)` 在调用方事务内 add + flush
- **消费任务**：`fwsort.scheduler.flush_outbox()`（Celery beat 30 秒一次）+ `flush_outbox_sync()` 同步入口（无 broker 兜底）
  - 拉 `status IN (0, 2) AND next_retry_at <= now` 的事件，FIFO
  - `dispatch_event(event)` 调 `async_es.index(...)`
  - 成功 → `mark_event_success`（status=1）
  - 失败 → `mark_event_failure`（retry_count+1，指数退避 1/2/4 分钟，超过 3 次转 10 分钟长退避）
- **ES 写入**：`fwsort.execution.es_writer.schedule_index_order_log(...)` 用 `asyncio.create_task(...)` 异步消费，捕获异常只记录不抛（fire-and-forget）
- **agent_router 集成**：`predict_and_vote` 同事务内同时：
  ```python
  db.add(build_order_log_event(log))   # outbox 入库（兜底）
  await db.flush()
  schedule_index_order_log(...)        # 异步 fire-and-forget（快速通道）
  ```
  outbox 入库失败仅 warning 日志，不阻塞主流程。

**验收**（d1_d2_smoke 步骤 5-6 + test_wp09_*）：
- 投票→下单 P99 实际 337ms（< 600ms 目标）
- `POST /api/admin/trigger/flush_outbox` → `{"success": 0, "failed": 0, "skipped": 0, "total": 0}`（无待发事件时正常）
- `test_wp09_outbox_dispatch_skips_already_success`：status=1 事件直接返回 True，避免重复 IO

## 4. 风险与遗留

| 风险 | 缓解措施 | 状态 |
| --- | --- | --- |
| 演示/生产模式 `is_demo` 字段在 `/api/info` 硬编码为 False/True，未读取 `settings.APP_DEMO_MODE` | D3 阶段统一：让 `/api/info` 与实际运行模式绑定 | 已记录 |
| Celery broker 在 dev 模式不可用，依赖 `apply().get()` 同步兜底 | 文档化；D5 部署时启用独立 worker 容器 | 已记录 |
| `flush_outbox` 在 SQLite 模式下用 `asyncio.run()` 启新循环，与 FastAPI event loop 解耦（避免循环冲突） | 后续可改为线程池 | 已实现但可优化 |
| outbox 表无清理策略，长期会膨胀 | D3 阶段与 `daily_cleanup` 合并清理 status=1 超过 7 天的记录 | 待办 |
| `_FakeSyncRedis` 在测试中无 `zrem` 方法，测试改为 ZSet 覆盖式重算 | 不影响真实 Redis | 已绕过 |
