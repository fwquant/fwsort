# 📌 智能体新增章节（不修改原需求，仅追加，供审阅）

> 以下内容由 `fuwen_dev_agent` 基于项目现状（fwsort V1.0）补充的**业务理解 + 落地开发计划**。原文档一字未动。审阅通过后再开工。

## 一、对需求的理解（智能体视角）

### 1. 角色与边界
- **用户身份**：本需求描述的是**"交易员"**（即登录后拥有执行账户的普通用户），不是平台管理员，也不是跟单者（follower）。
- **入口**：登录后落地页 = `http://localhost:8000/`（首页 Tab「🌍 总榜单 / 👤 我的榜单」）。
- **三大核心动作**：①管理自己的执行账户（增删改查+启停）② 决定自己是否被公开到总榜单（开关跟单）③ 查看自己的执行成绩（我的榜单）。
- **隐含的"主账号"**：需求中的"主账号"在项目里实际对应**登录用户（User）**。`User` 是聚合主体，多个 `ExecutionAccount` 挂在同一个 `User` 下面。开关是**主账号级别**的，影响该 User 下所有执行账户的可见性。

### 2. "执行账号管理"的关键字段补全
原需求列出 `账户名 / 交易平台 / 投入总金额 / 交易标 / 下单时间与下单详细标 / 每次下单金额 / 信号(UP/DOWN)`。对照现有 `ExecutionAccount` 模型：
- ✅ 已有：`name / platform / initial_balance / current_balance / status / account_type / risk_frozen`
- ❌ **缺失**：
  - `target_url`（交易标 URL，如 polymarket 二元合约链接）
  - `target_symbol`（标的编码/简称，可由 URL 解析）
  - `signal`（当前信号值，UP/DOWN/NEUTRAL）
  - `signal_source`（信号来源：random / gpt-4o / claude / gemini / moa）
  - `signal_updated_at`（信号最近更新时间）
  - `order_amount_usd`（每次下单金额，区别于 `initial_balance` 投入总额）
  - `last_order_at`（最近一次下单时间）
  - `public_enabled`（**该账户是否参与总榜单**，与"主账号公开"两个粒度都需要）

### 3. "开关跟单"的两种粒度（重要澄清）
原需求第 13 行说"主账号管理支持打开与关闭用户跟单功能"。这里"跟单"在不同粒度下含义不同：
- **粒度 A：被跟单可见性（公开）**——控制本主账号（User）的成绩是否上**总榜单**让所有人看到。这是需求字面意思。
- **粒度 B：跟单可订阅性**——控制其他用户能否**订阅**本用户的信号去跟单。这跟"公开"通常绑定，但也允许"公开可见但禁止跟单"的细粒度。

**建议实现**：在 `User` 表增加 `share_to_global`（粒度A，控制总榜单可见）+ `allow_follow`（粒度B，控制可被订阅）。两个开关独立、默认都开启，关闭后**该用户的所有执行账户**从总榜单聚合中排除，跟单接口拒绝新订阅。**主账号的"我的榜单"始终可见**（自己总能看自己）。

### 4. "定时任务-自动化执行"流程拆解
原需求 17-23 行实际上是**一条 Celery 定时流水线**：
1. 扫描所有 `status=0`（启用）且 `account_type=0`（模拟盘）优先 + `public_enabled=1` 优先 的执行账户
2. 对每个账户：
   - 读 `target_url` 解析标的状态（如 polymarket 的 YES 当前价、剩余到期时间）
   - 拉/生成信号：当前 `random.choice(["UP","DOWN"])`；后续接多智能体 MoA 聚合
   - 调 `OrderSimulator.place(side=signal, amount=order_amount_usd, expected_price=...)` 下单
   - 写 `OrderLog`（ES 索引 + Postgres 镜像）
   - 累加 `StrategyPerformance`（日/周/月/总）
3. 触发"分析整理执行账号数据"——根据订单执行时间、价格、数量、手续费、滑点，更新 `execution_score`，进而更新 `composite_score`，重算 `RankType.REALTIME` 的 Redis ZSet。

### 5. "定时任务状态列表"界面
原需求 22 行要求新增一个**任务状态可视化界面**，与"系统控制台"分开：
- 按账户维度展示：账户名、平台、最后运行时间、运行结果（成功/失败/运行中）、累计成交笔数、当日盈亏、信号最近值
- 按任务维度（次级 Tab）：Celery 任务名、上次触发时间、状态、平均耗时、错误信息
- 实时性：前端 5 秒轮询 `GET /api/execution/task-status`

### 6. 标的（target_url）解析的边界
- **polymarket**：URL 形如 `https://polymarket.com/zh/event/btc-updown-5m-1785301500`，需要解析 event slug → 当前 YES/NO 价格 → 到期时间。`polymarket_client` 已有，需要补充 `parse_event_slug` 工具。
- **okx 现货**：URL 形态完全不同，建议本期先**只跑通 polymarket**（原需求 21 行明说"默认先跑通 polymarket"），okx 占位但不实际下单。

### 7. 与现有 V1.0 模块的对接点
- 智能体：已落地的 `core/agents/hermes_moa.py` 仅做"出信号"，下单交给 `core/execution/simulator.py`。本次需求正好补全"信号 → 下单 → 记账"的完整链路。
- 跟单：`FollowSubscription` / `FollowOrder` 已有，但需要在 `subscribe` 接口增加 `if not leader.allow_follow: raise ForbiddenError`。
- 排行：总榜单聚合 `/api/ranking/global` 已实现，**只需在 SQL 加 `WHERE user.share_to_global = 1`**。
- 我的榜单：策略级排名 `/api/ranking/my` 已实现，本期**不动**。
