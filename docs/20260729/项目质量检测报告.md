## 二、安全（Security）

### 🔴 S-1 生产 CORS 全开（`main.py:70-76`）
- **现状**：`allow_origins=["*"]` + `allow_credentials=True`。**这是非法组合**，浏览器将直接拒绝；但后端实际仍会接受请求，CSRF/凭据泄露风险高。
- **建议**：依据部署域名收敛白名单；正式环境关闭 `*`；可按环境拆 `APP_CORS_ORIGINS`。

### 🔴 S-2 默认 JWT 密钥仍是 `change-me`（`config.py:24` + `.env.example:7`）
- **现状**：`APP_SECRET_KEY` 默认值是 `change-me`，示例文件里也仅给了固定占位串。一旦部署者忘记覆盖，所有 JWT 可被伪造。
- **建议**：启动时若 `APP_ENV=production` 且密钥仍为 `change-me` / 长度 < 32，直接拒绝启动；用 `secrets.token_urlsafe(32)` 生成随机串并提示写入 `.env`。

### 🔴 S-3 缺少登录限流（`auth_router.py` 整文件）
- **现状**：`/api/auth/login`、`/api/auth/register`、`/api/auth/refresh` 完全没有频控和失败计数。攻击者可以无限爆破邮箱/弱密码。
- **建议**：增加基于 Redis 的滑动窗口限流（IP + 邮箱双维度），登录失败 5 次锁定 15 分钟；register 同 IP 限速。

### 🔴 S-4 Refresh Token 接收方式不严谨（`auth_router.py:163-184`）
- **现状**：`refresh_token` 直接通过 `POST` body 字段接收（裸字符串），缺少来源校验和防重放。
- **建议**：把 refresh token 纳入 `OAuth2PasswordRequestForm` 或自建 cookie + `HttpOnly + Secure + SameSite=Strict`；服务端记录 `jti` 拉黑名单（Redis）。

### 🟠 S-5 密码复杂度策略过弱（`auth_router.py:134`）
- **现状**：`len(new_password) < 6` 即通过；只检查长度，不要求数字/字母/特殊字符组合。
- **建议**：至少 8 位 + 字母 + 数字；可用 zxcvbn 评分拒绝弱密码（"12345678" / "password"）。

### 🟠 S-6 用户/账户删除"假删除"导致数据悬挂
- `agent_router.py:269-302` 删除 `ExecutionAccount` 时，把相关历史 `AgentPrediction` 等写为 `if False else None`（死代码），实际并没解除外键。后续新增 `account_id` 关联查询会因历史脏数据报错。
- 建议：真正把 `account_id` 置 NULL，或改为软删除 `deleted_at`。

### 🟠 S-7 内部调用穿越封装（`agent_router.py:378`）
- `sync_execution_status` 通过 `_gateway._get_okx()` 拿到内部 OKX 客户端并 `client.get_order(...)` 直调。破坏了封装，且当 Gateway 内部重构时这里会无声崩。
- 建议：在 `ExecutionGateway` 暴露明确的 `sync_order(order_id)` 接口。

### 🟠 S-8 公开接口泄露内部细节
- `/api/rental/agents` 公开（`rental_router.py:21-37`）：暴露 model 字段 → 容易让外部对模型针对性提问越狱。
- `/api/ranking/global`/`list`/`history`/`change` 无任何权限，但 history/change 返回的是 mock 随机数据（`ranking_router.py:477-507`），会误导公众/SEO。
- 建议：内部 API 加 `current_user`；mock 接口加 dev 守卫。

### 🟠 S-9 私钥/助记词等敏感字段直接进 `.env`
- `POLYMARKET_PRIVATE_KEY` / `OKX_SECRET` 通过环境变量明文落盘（`config.py:66-71`）。一旦仓库误提交或 .env 泄露，资金全损。
- 建议：接入 Vault / KMS 或硬件加密；至少在 .env.example 写强警告；`.gitignore` 校验。

### 🟡 S-10 缺少全局安全头
- 没有 `X-Content-Type-Options`、`X-Frame-Options / CSP`、`Referrer-Policy`、`Permissions-Policy`、`Strict-Transport-Security`。
- 建议：增加安全头中间件；至少为生产环境开启。

### 🟡 S-11 Pydantic 字段未限制 `extra` 行为
- `RegisterReq` 等未显式 `model_config = ConfigDict(extra="forbid")`。多余字段会静默忽略，前端可见后端真实结构。
- 建议：所有入参 schema 设 `extra="forbid"`。

### 🟡 S-12 数据库初始化接口可被未授权调用
- `POST /api/admin/init-db`、`seed-admin` 等端点无权限校验（`admin_router.py:41-67`）。任何匿名者能创建管理员。
- 建议：与 `trigger-task` 一样加 `require_admin`。

### 🟡 S-13 错误响应可能泄露栈/字段
- 422 转换时打印 `raw_message`（`main.py:206`），debug 模式会回原始英文。`APP_DEBUG=false` 时也应清理。

### 🟢 S-14 Token 存 localStorage
- 已知 XSS 即可拿走 JWT。建议演示版可保留，生产版切 cookie + HttpOnly。

## 三、功能完整性（Functionality）

### 🟠 F-1 演示/生产模式未做数据层隔离
- `main.py` 的 `/demo/*` 与 `/` 共享同一份 DB、Redis、ES（`settings` 完全相同）。演示模式只是"打了一个 Badge" + 拦截了导航。
- 实际风险：在演示页"删除账户/触发投票"会真正改动生产数据。
- 建议：通过 `APP_DEMO_MODE` 配置项，让演示路由全部走 fake / 临时 SQLite + 内存 Redis。

### 🟠 F-2 投票引擎与下单之间无事务一致保障
- `agent_router.py:80-145`：vote 入库 → 调外部下单 → ES 双写。若下单后 ES/DB 任一失败，订单会处于"DB 有 / ES 无"的不一致。
- 建议：引入 outbox 模式或 Celery 异步重试；ES 写入改为后台任务。

### 🟠 F-3 跟单"自动执行"路径缺失
- `follow_router.py:234-264` 提供 `execute_follow_copy`，但没有 scheduler 任务真正调用它（搜索 `scheduler.py` 任务列表应包含 `follow_copy_loop`，未在 admin/trigger 中暴露）。
- 用户订阅后看不到任何跟单成交记录。
- 建议：新增 `follow_copy_loop` Celery 任务，并提供手动触发按钮。

### 🟡 F-4 通知中心没有主动推送机制
- 仅提供轮询接口 `notifyList` + 前端 1 分钟 `setInterval`（`app.js:55`）。风控事件、跟单成交、榜单变化若没及时轮询会感知不到。
- 建议：未来接入 SSE 或 WebSocket；当前至少把轮询降为 30s 且只读未读。

### 🟡 F-5 排行榜段位/权重调整后未触发重算
- `config_router.py:60-92` 更新权重后没刷新榜单 ZSet；`ranking_router.py:list` 仍用旧分。
- 建议：权重变更后调用 `ranking_engine.refresh_all()` 或重置 Redis ZSet。

### 🟡 F-6 执行账户详情页缺数据
- `detail.html` 展示的是排行榜维度的指标，看不到"该账户的订单流水 / P&L 曲线 / 跟单贡献"。
- 建议：详情页增加：订单表（已存在 `execution/{uid}` 但未挂入）、净值曲线、跟单贡献。

### 🟡 F-7 智能体租用按次模型扣费实现不一致
- `rental_router.py:64-80` 提到 `used_calls` 求和但只 +1 一次，逻辑没问题；但**实际没有真扣费**（价格字段 `price_per_call` 仅作展示），用户没有余额、没有支付通道。
- 建议：先实现"账户余额表 + 扣费流水"，或明确标注"当前为试算"。

### 🟡 F-8 账户管理页（profile）功能薄弱
- 仅展示 ID/邮箱/角色/注册时间/统计；缺两步验证（2FA）、登录设备、API Key 管理、安全日志、操作历史。
- 建议：增加"最近登录"、"活跃会话"、"API Key"（用于外部数据导出）。

### 🟡 F-9 `seed-mock` 没有去重
- 多次点击会创建 N×多次账户 + 投票。需增加"已播种过则拒绝"或"清空后重播"开关。

### 🟢 F-10 没有"找回密码"流程
- 邮箱注册但无邮件通道；忘记密码 = 失去账户。
- 建议：至少先加"管理员后台重置"。

## 四、性能（Performance）

### 🔴 P-1 关键查询缺索引
- `StrategyPerformance` 仅 `(period_type)` + `composite_score` 索引（隐式）；`account_id+period_type` 联合索引缺失，榜单主查询会扫全表。
- `OrderExecutionLog.uid+created_at` 复合索引缺失 → 订单流水翻页将随数据量增长线性变慢。
- `FollowSubscription(subscriber_id, leader_uid, status)` 缺联合索引。
- 建议：补齐联合索引（见下方"建议索引清单"）。

### 🔴 P-2 N+1 / 隐式全表扫描
- `follow_router.py:28-36` 直接 `select(StrategyPerformance, ExecutionAccount).join(...).order_by(composite_score.desc()).limit(N)`，无分页游标；`global_ranking` 同。
- `notification_router.py:71` `mark_all_read` 先 `select` 再逐条 update，可改为 `UPDATE ... SET is_read=true WHERE user_id=?` 一次性更新。
- 建议：把 `mark_all_read` 改为 bulk_update；榜单用 keyset 分页（`(score, id) < (last_score, last_id)`）替代 offset。

### 🟠 P-3 启动时构造 MoA / Simulator 单例，但调用前未做连接健康检查
- `_moa = build_hermes_moa()` 在 `agent_router.py:28` 模块级 import 时构建。任意一智能体 SDK 抛错会让整个服务起不来。
- 建议：惰性初始化 + 启动自检 + 出错降级 mock。

### 🟠 P-4 模板渲染用磁盘 I/O 同步读取
- `main.py:308-316` `_render_page` 每次请求都 `open(...).read()`。高并发下会成为瓶颈。
- 建议：进程启动时一次预读缓存到 `dict`；或加 LRU 内存缓存。

### 🟠 P-5 全局 `lifespan` 关闭 ES 时静默吞错
- `main.py:54-57` `pass` 掉所有异常，难以排查；并且 ES 未对账时索引顺序问题没暴露。
- 建议：分级记录 warning/error；fail-fast 选项。

### 🟠 P-6 榜单数据未充分利用缓存
- `ranking_router.py:list` 走 Redis ZSet，但 `history / change / global` 全是即时 DB + MOCK 计算。
- 建议：history/change 加 `set_cached(rank_key, json, 60)`；分页缓存 `list?page=X`。

### 🟡 P-7 模拟器同步 `time.sleep`
- `simulator.py:60` `time.sleep(latency/1000)`：会阻塞 event loop（被 `await` 调用会阻塞整个 worker），并发下吞吐量断崖。
- 建议：改成 `await asyncio.sleep(latency/1000)`。

### 🟡 P-8 同步与异步两套连接池
- `database.py` 同时建 sync + async 各一份，连接池都拉满时会占双倍资源。
- 建议：Celery 复用短生命周期 + 池化；或合并为 async + run_in_executor。

### 🟡 P-9 ES 写为同步等待
- `agent_router.py:148-168` `await index_order_log(...)` 是阻塞主流程；ES 抖动会拖慢下单。
- 建议：后台任务队列（Celery / asyncio.create_task）异步消费。

### 🟡 P-10 前端首屏 JS 未分块
- `accounts.html` / `index.html` 等加载 `app.js` + 业务 js + `lib/echarts.min.js`，整体 ~ 1MB+。
- 建议：echarts 拆 `import()` 懒加载；`defer` + 关键 JS 优先级。

### 🟢 P-11 `accounts.js` 全量客户端过滤
- 数据量大时（> 500 行）会卡顿；可改为虚拟列表 + 服务端过滤。

### 🟢 P-12 Polling `setInterval(refreshNotifyBadge, 60_000)` 整页
- 每个标签页都 60s 拉一次，服务端压力被放大。SSE 是更优解（见 F-4）。

## 五、交互界面（UI / 美观 / 易用）

### 整体观感（积极项）
- ✅ FWUI 主题统一，玻璃质感/渐变/动画风格明确；
- ✅ 暗紫/明亮双主题切换完备；
- ✅ 演示/生产模式独立路由 + 醒目角标（已完成）；
- ✅ 表头排序、搜索、视图切换已经较为完善；
- ✅ 弹框已统一为 FWUI（玻璃质感 + 类型图标 + 渐变按钮）。

### 🟠 U-1 移动端可访问性不足
- 多个按钮缺少 `aria-label`（如 `data-theme-toggle`、`#btn-notify`）。
- 颜色对比：通知小红点（`#btn-notify` 红色徽章 + 黄色 🔔）在明亮主题下对比度偏低，色弱用户不易感知。
- 建议：所有 icon-only 按钮加 `aria-label`；关键状态色用对比度 ≥ 4.5:1。

### 🟠 U-2 通知中心交互卡顿
- `app.js:79-93` 一次性 `innerHTML` 拼接 30 条 + 没有虚拟滚动，条目增多后会卡。
- 建议：分页加载 + 滚动到底再请求；或加"加载更多"按钮。

### 🟡 U-3 表单校验不统一
- 注册表单把 `2-64 字符` 写在 HTML 提示里（`app.js:184-187`），但后端 `RegisterReq` 的 `nickname` 用 `min_length=2, max_length=64`；登录页直接硬编码 6-64。后端是真理之源，前端硬编码易漂移。
- 建议：从 `/api/auth/constraints` 拉一份配置，前端渲染。

### 🟡 U-4 列表/卡片切换状态不持久
- `accounts.js` 的 `_viewMode` 是页面级内存变量，刷新即丢失。
- 建议：localStorage 记住用户偏好（follow.js 已做，accounts.js 没做）。

### 🟡 U-5 加载/空态/错误态三态不齐
- 多数页面只有 `loading` + 错误态；缺少"无搜索结果"空态（如搜索后过滤为 0 条）。
- 建议：统一 `fwui-empty-card` 三态：empty / loading / error。

### 🟡 U-6 移动端工具栏仍然拥挤
- `accounts.html:27-48` 工具栏在 480px 下还是横排，建议移动端折叠成"筛选"抽屉。
- 建议：移动端用"筛选"按钮弹一个下拉/抽屉，包含搜索/类型/视图。

### 🟡 U-7 主题切换按钮文案不稳定
- `app.js:32` 初始 `明亮`/`暗紫`，取决于当前主题。语义是"切到相反"还是"切到指定"？用户初次看不明白。
- 建议：按钮文案固定为"🌗 切换主题"，hover 时显示目标。

### 🟡 U-8 详情页缺直接下单 / 加自选入口
- `detail.html` 只能"看"，不能"立即订阅 leader"或"加自选"。

### 🟡 U-9 数据图表色彩与主品牌渐变不一致
- `ranking_detail.js` 使用 ECharts 默认色块，跟暗紫主色脱节。
- 建议：封装 `fwuiChartTheme` 主题对象统一注入。

### 🟡 U-10 移动端长列表无骨架屏
- 加载时只有 `⏳ 加载中...`，白屏时间感知长。
- 建议：加 skeleton 占位（浅灰矩形 + shimmer）。

### 🟢 U-11 多语言缺位
- 文案全部硬编码中文，国际化场景无法扩展。
- 建议：抽出 i18n 表（zh-CN / en-US）。

### 🟢 U-12 页面标题缺层级
- 所有页面 `<title>` 都只是"账户/榜单/跟单..."，SEO 与浏览器收藏夹体验弱。
- 建议：标题加项目名后缀：`账户 · 福纹排行榜`。

## 六、架构 & 工程化

### 🟠 A-1 缺乏测试覆盖
- `tests/` 目录的 `test_ranking_engine / test_voting / test_execution_quality` 是单元测试，但**没有 auth / API / 端到端**。`validate_system.py` / `e2e_v1.py` 是手工验证脚本，没有接 pytest。
- 建议：补 pytest + httpx.AsyncClient 测试套件；CI 跑 lint + test + coverage（≥ 70%）。

### 🟠 A-2 日志不规范
- `main.py` 配置了 loguru InterceptHandler，但 `agent_router.py:400` 用了 `logger.warning` 而 `fwsort/__init__.py` 没有导出 logger；不少路由（`auth_router` / `rental_router` / `follow_router`）未记录关键操作（登录、订阅、扣费）。
- 建议：统一 `from loguru import logger`；关键操作 `bind(user_id=...)` 输出结构化日志。

### 🟠 A-3 没有 API 文档
- FastAPI 自带 Swagger，但 `/docs` 在生产未禁用，攻击者可枚举端点。
- 建议：生产环境 `docs_url=None`；或加 Basic Auth 守护。

### 🟠 A-4 Celery 任务未注册 worker
- `scheduler.py` 定义了 `daily_snapshot / refresh_realtime_rank / archive_hot_to_cold / daily_cleanup`，但 `docker-compose.yml` 没看到 `celery worker / celery beat` 服务。
- 建议：补齐 compose 服务；否则定时任务全部失效。

### 🟡 A-5 `requirements.txt` 锁版本过于严格
- `fastapi==0.139.2` 这种紧锁版本会在生产升级时大麻烦；`>=` 与 `==` 混用。
- 建议：用 `pip-compile` / `uv` 生成锁文件，分 `requirements.txt`（通用）和 `requirements.lock`。

### 🟡 A-6 配置项散落
- 风控阈值、订单金额、段位阈值硬编码在 `voting.py`、`ranking_engine.py`、`.env`。管理员页面（`config_router.py`）能改权重但不能改风险/段位。
- 建议：把阈值/段位纳入 `weight_config` 同款的可调表。

### 🟡 A-7 没有前端构建/打包
- 直接引用 `lib/echarts.min.js` 1MB+，且无 hash、无 CDN 缓存策略。
- 建议：迁移到 Vite，打包产物加 hash。

### 🟡 A-8 错误处理风格不统一
- 一部分用 `raise FwsortError("...")`、一部分 `return fail(message=...)` 混用；前端 `api.js` 三层兜底才完成。
- 建议：把 `fwsort.response.fail` 内部走异常，由全局 handler 统一序列化。

### 🟢 A-9 `LICENSE` / `README` 缺失
- 仓库根有 `LICENSE` 但 README 不在根目录（开发文档在 `docs/`）。外部协作者上手难。
- 建议：根目录补 README.md，5 分钟跑通。

### 🟢 A-10 临时调试文件
- 仓库根仍有 `1.html / 1.md / login.json / _test1.json / ranking.json / admin_token.txt / uvicorn.err / server.err` 调试残留。
- 建议：纳入 `.gitignore` 并清理；其中 `admin_token.txt` 是高危凭据，应立即删除并轮换。
